## Observed results (raw values, no interpretation)

### Ca 1 — CVE-2017-1001000 (`GET /wp-json/`)

| State | File | Status | `"routes"` in body | Content-Type |
|---|---|---|---|---|
| WP 4.7.1 (8711) | `8711-wp471-GET-wp-json.txt` | `200 OK` | **absent** | `text/html` |
| WP 4.7.2 (8712) | `8712-wp472-GET-wp-json.txt` | `200 OK` | **absent** | `text/html` |
| WP 4.7.1 (8711) | `8711-wp471-GET-rest-route-index-SUPPLEMENTARY.txt` | `200 OK` | present | `application/json` |
| WP 4.7.2 (8712) | `8712-wp472-GET-rest-route-index-SUPPLEMENTARY.txt` | `200 OK` | present | `application/json` |

**Deviation D-V2-1 (Ca 1): the mandated request does not produce JSON on this lab.**
Both WordPress databases have an **empty `permalink_structure`** (plain permalinks; confirmed by
`SELECT option_value FROM wp_options WHERE option_name='permalink_structure'` → empty). With
plain permalinks WordPress does not rewrite `/wp-json/...` to the REST server, so `GET /wp-json/`
falls through to the **front page** and returns `200 text/html` with **no `"routes"` key**. The
mapping's `true_when` for `probe_rest_root` ("200 **and** body JSON `routes`") therefore **cannot
fire from `GET /wp-json/` in this deployment**, for either state — the status alone is a
false-positive trap (200 ≠ REST reachable).

The same REST index is reachable on both states the plain-permalink way
(`GET /?rest_route=/`, captured as the SUPPLEMENTARY files) → `200 application/json` with
`"namespaces":["oembed/1.0","wp/v2"]` and a non-empty `"routes"` object. The original
CVE-2017-1001000 reproduction in this lab also used the `?rest_route=` form
(`experiments/26cve/_batch3-stack/scripts/repro/15-cve-2017-1001000.sh`).

Researcher/engineer decision needed (not taken here): change the probe request to the
plain-permalink REST index, or enable pretty permalinks in the lab stack. The lab state was
**not** changed.

### Ca 2 — CVE-2024-10924 (POST `two_fa/skip_onboarding`, empty body)

| State | File | Status | JSON error code |
|---|---|---|---|
| 9.1.1.1 + 2FA ON (8081) | `8081-2fa-on-POST-skip_onboarding.txt` | `400 Bad Request` | `rest_missing_callback_param` |
| 9.1.1.1 + 2FA OFF (8081) | `8081-2fa-off-POST-skip_onboarding.txt` | `404 Not Found` | `rest_no_route` |
| 9.1.2 fixed + 2FA ON (8082) | `8082-fixed-9.1.2-2fa-on-POST-skip_onboarding.txt` | `400 Bad Request` | `rest_missing_callback_param` |
| 9.1.1.1 + 2FA ON (8081), literal work-package URL | `8081-2fa-on-POST-literal-wp-json-URL-DEVIATION.txt` | `200 OK` | — (`text/html` front page) |

The first two rows are exactly the work-package expectations. **2FA was restored to ON on 8081
after the OFF capture** (verified: `login_protection_enabled=1` on both instances).

**Deviation D-V2-2 (Ca 2): the work-package route string/URL does not work on this lab.**
(a) The plugin registers its REST namespace as **`reallysimplessl/v1`**, not
`really-simple-security/v1` (`security/wordpress/two-fa/class-rsssl-two-factor-on-board-api.php`,
`self::NAMESPACE`); the pilot repro script used the same correct route. (b) As in Ca 1, the lab
uses plain permalinks, so the plain-permalink route form
`/?rest_route=/reallysimplessl/v1/two_fa/skip_onboarding` is used and the literal
`/wp-json/really-simple-security/v1/two_fa/skip_onboarding` URL returns the HTML front page with
`200` (the fourth file above records that trap).

**Deviation D-V2-3 (Ca 2, fixed state): the fixed build does NOT return 500 for this probe.**
With an **empty** body the patched 9.1.2 answers `400 rest_missing_callback_param` — the same
status/code as the vulnerable 2FA-ON state — because WP validates the required args
(`user_id`, `login_nonce`) before the fixed callback runs. The pilot's `500` (`wp_die()`) was
produced with the required params *supplied*; it is not visible from an empty-body route probe.
The capture is the verbatim observed response, not an assumed one.

Toggle command used (same as the pilot `experiments/pilot-3cve/scripts/11-wp-2fa.sh`, ground
truth only, never a method input):

```bash
docker run --rm -u 33 --network pilot-net -v ~/pilot-lab/wordpress/vuln/html:/var/www/html \
  -e WORDPRESS_DB_HOST=db:3306 -e WORDPRESS_DB_NAME=wp_vuln -e WORDPRESS_DB_USER=labuser \
  -e WORDPRESS_DB_PASSWORD=<lab-db-pass> -e WORDPRESS_TABLE_PREFIX=wp_ wordpress:cli-php8.2 \
  wp eval "rsssl_update_option('login_protection_enabled', 0);"   # 0 = OFF, 1 = ON (restored)
```

**Deviation D-V2-4 (Ca 3): the two databases are not ID-comparable, and the batch2 stack was not
in the 2.6.6/2.6.7 state when this session started (restored — see D-V2-5).**
`?page_id=6` is the UM registration page only on the vulnerable instance. In the fixed database
`um_core_forms = {"register":6,"login":7,"profile":8}` → **post 6 is the registration *form*
(`um_form`), not a page**, so `?page_id=6` returns `404`; the fixed instance's UM registration
*page* is **post 12** (`[ultimatemember form_id="6"]`), and a leftover pre-UM "Register" page
post 5 points at form 7 (the login form). On the vulnerable instance `um_core_forms = {register:7,
login:8, profile:9}` and the register page is post 6 (`[ultimatemember form_id="7"]`).
Consequently the rendered field-name suffix differs (`user_login-7` vs `user_login-6`); it is the
fixture form id, not a security property. Matching markers on both states: `um-form`, the
`user_login-<form-id>` field, and `_wpnonce` — both states return `200` and render an open
registration form.

### Deviation D-V2-6 — stacks restarted (resource-scoped)

like the pilot stack). They were brought up with **only the needed services**:


memory use on the 7.7 GiB VM; they are unrelated to the three cases and their ports are not needed.
The pilot stack was already `Up`.
